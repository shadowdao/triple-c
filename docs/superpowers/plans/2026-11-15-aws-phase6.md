# AWS Host Phase 6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the Fargate workspace feature set: EFS storage, Copy-at-connect, setup scripts, a cost estimate, and the four phase 5 deferrals (port mappings, LLM gateway sidecar, the admin's maximum workspace lifetime, quieter WIP and clone handling).

**Architecture:** Everything builds on phase 5's shapes: one secret per project carries all project data (P1); the task definition gains a second EFS volume (EFS mode) and an optional `gateway` sidecar container; the entrypoint's `aws` mode gains a setup-script runner, a lifetime cap and a re-runnable "apply credentials" script for Copy-at-connect; the app follows clone and setup progress through the agent after connecting, forwards port mappings over the existing socat-over-attach tunnel, and prices a workspace from the AWS Pricing API.

**Tech Stack:** Rust (aws-sdk-ecs/-efs/-secretsmanager, + aws-sdk-pricing), OpenTofu (environment module), bash entrypoint and container scripts, React/TS.

**Spec:** `docs/superpowers/specs/2026-11-13-aws-ecs-host-design.md` (Storage, Secrets and uploads → Copy at connect, Snapshots → setup script, Multi-user accounts → Cost visibility, Lifecycle → idle auto-stop "the admin's maximum lifetime is a hard cap", Feature compatibility → port mappings and LLM gateway sidecar). Phase 5's rulings P1–P9 and R1–R11 (spec "Phase 5: rulings") still bind.

## Decisions this plan makes (rulings)

- **Q1. EFS mode uses a second access point mounted at `/workspace`.** Root `/triple-c/<owner_key>/<project>/workspace` would nest inside the home access point, so it gets a sibling root: `/triple-c-workspaces/<owner_key>/<project-component>`, POSIX 1000:1000, 0700, on the user's own file system. Hybrid's home access point and symlinks stay as they are; EFS = Hybrid + `/workspace` on EFS. Store-owned field `workspace_access_point_id`. Switching EFS → Hybrid/Ephemeral leaves the workspace access point (and its files) in place until "Remove AWS resources" removes it, said in the UI.
- **Q2. Copy-at-connect keeps settings, moves credentials.** With `secrets_delivery: CopyAtConnect` the project secret still carries non-credential project data (P1) and the agent token; it drops `TRIPLEC_FILES` and every credential env pair (`SECRET_ENV_KEYS` and all custom env values). After each connect the app uploads the files to `/tmp/.host-ssh` / `/tmp/.host-ca` and an env file to `/dev/shm/triple-c/connect.env` (root, 0600) through the agent, then runs a new root script `triple-c-apply-connect` (CA install, SSH merge, git credential helper — the entrypoint's own functions, moved into `/usr/local/lib/triple-c/entrypoint-lib.sh` so both call the same code) and re-runs the clone for repos that failed. Terminal sessions the app opens add the connect env to their `ExecSpec.env`. Scheduled jobs while the app is closed don't get credentials (spec says so; the UI says so). The spec's "persist to EFS" opt-in is **not** built.
- **Q3. Setup script: AWS only, run as `claude` after the clone, before the workspace counts as ready.** Stored in `AwsWorkspaceConfig.setup_script` (≤ 32 KiB), delivered as payload key `TRIPLEC_SETUP_SCRIPT` (P1). The entrypoint writes it to `/run/triple-c-setup/script`, runs `bash -e` as `claude` (who has sudo for apt) with a 30-minute timeout after the background clone finishes, logging to `/run/triple-c-setup/log` and writing `/run/triple-c-setup/status` (`running` | `ok` | `failed <code>`). The idle watcher treats a running setup like a running clone.
- **Q4. Start follows clone and setup.** After "Connecting…", the start command polls one new agent-side status read (`triple-c-workspace-status`, JSON of clone + setup state) every 2 s and emits each new state/log line as `container-progress` ("Cloning repos… (1/3)", "Running setup script…", last log line), until both are done or 35 minutes pass. A failed clone or setup does not fail the start: the project is Running and a warning toast carries the last lines. Project Home Overview shows the same status for AWS projects (still cloning / setup failed).
- **Q5. Cost estimate from the Pricing API, cached a day.** `pricing:GetProducts` (Resource `*`; the API has no resource-level permissions) goes into `workspace-user-tasks.json`. Prices come from the `AmazonECS` service code in `us-east-1`, filtered to the region and Fargate vCPU-hours / GB-hours / ephemeral storage GB-hours for x86 and ARM; cached on disk per region for 24 h. Spot isn't in the Pricing API: the UI shows the on-demand figure with "Spot is usually up to 70% cheaper". EFS storage isn't per-hour and isn't estimated. Shown in HostSection (as you configure) and Project Home Overview (while running). Denied or offline → "Estimate unavailable", never an error.
- **Q6. Port mappings reuse the auth bridge's tunnel.** `auth_bridge::tunnel` already forwards a host loopback port into the container over socat-over-attach, which works through the agent. Generalise `PortForward::bind` to take a host port and a container port. AWS mappings bind **loopback only** (Docker binds 0.0.0.0; the UI says so), TCP only (UDP refused for AWS projects), opened after connect and closed on stop/exit. No new `/v1/tunnel` client.
- **Q7. LLM gateway as a sidecar, opt-in per project.** `AwsWorkspaceConfig.gateway_sidecar: bool`. When on, the task definition adds a non-essential `gateway` container running the app's pinned LiteLLM image (`docker::gateway` registry ref, digest-pinned), with `memoryReservation` 512 MiB; its config YAML and keys arrive as payload keys `TRIPLEC_GATEWAY_CONFIG`, `TRIPLEC_GATEWAY_API_KEY`, `TRIPLEC_GATEWAY_MASTER_KEY` (rendered with the same `render_config` as Docker, keys via `os.environ/…` references) and the container's command writes the config to `/tmp` and starts LiteLLM on `127.0.0.1:4000`. The project must use the OpenAI-compatible backend; the app then points `ANTHROPIC_BASE_URL` at `http://127.0.0.1:4000` and `ANTHROPIC_AUTH_TOKEN` at the master key, regardless of the base URL typed for local use. The task's CPU/memory must leave room: the minimum for a sidecar project is 1 vCPU / 2 GiB (validated).
- **Q8. Lifetime cap is enforced inside the workspace (advisory), set per environment.** Environment module variable `max_workspace_hours` (0 = no cap, default 0) → record field `max_workspace_hours` (record schema stays 1; unknown-field tolerant parser already); `ENVIRONMENT_MODULE_VERSION` 1 → 2 so existing environments show "Update available". The app passes `TRIPLEC_MAX_LIFETIME_MINUTES`; the idle watcher stops the task when it's reached — WIP push first (best effort, 90 s), then stop even if the push failed — with exit status 76 (`StopKind::LifetimeCap`, toast "Stopped: the environment's maximum workspace lifetime"). The UI shows the cap in HostSection. **This is advisory**: a workspace user has sudo inside their own task and could disable it. Server-side enforcement (a scheduled Lambda that stops old tasks) is listed as a follow-up, not built. (Chosen by the user 2026-11-15.)
- **Q9. One WIP branch per task run, updated in place.** The branch becomes `triple-c/wip/<task-start-stamp>-<task-id-8>` (stamp written by the entrypoint at start into `/run/triple-c/run-id`; Docker/no-task fallback keeps today's per-push stamp); later pushes in the same run overwrite it (`+` refspec — the branch is ours alone), and a push whose tree equals the last one pushed for that repo in this run is skipped (tree hash kept in `/run/triple-c/wip-last/<folder>`).

## Global Constraints

- Everything in the phase 5 Global Constraints still holds (no `aws_config::defaults`; three tag keys only; names built in `aws/tofu_modules.rs`; no project data in task definitions — P1; container `workspace`; health check unchanged; the CPU/memory table incl. 256 → 512, 1024 or 2048 MiB; host/ boundary tests; policy + checks + README together, ≤ 6,144 characters each; three-part command registration; serde defaults with TS mirrors; live tests only through the scratchpad `awsx` wrapper, everything cleaned up, total spend cap $10).
- Docker behaviour unchanged unless a task says otherwise; every entrypoint addition gated on `TRIPLEC_HOST=aws`.
- New payload keys use the `TRIPLEC_` prefix (reserved since phase 5) and stay under the 64 KiB secret cap; the sizes add up (setup script ≤ 32 KiB + gateway config ≤ 8 KiB), so the cap error must name what is large.
- Root-run entrypoint code never follows a link the `claude` user controls (phase 5 hardening rule).

## Review Focus

1. A Copy-at-connect project started while the app is closed (scheduler) or before the first connect: private clones fail cleanly, the workspace still starts, and connecting later clones them — Task 6.
2. A setup script that hangs or needs input: bounded by its timeout, stdin is `/dev/null`, the start finishes with a warning, idle stop still works afterwards — Task 4.
3. A project switched between Hybrid and EFS with repos already present: no silent data loss, the UI says where the old files are — Task 3.
4. Two port mappings to the same host port, or a host port already in use on this machine: a clear per-mapping error; the other mappings still work — Task 7.
5. Pricing API slow/denied/offline: the config UI never blocks or errors — Task 9.
