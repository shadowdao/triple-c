# AWS Host Phase 7 (ECS on EC2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A project can run on its owner's dedicated EC2 capacity instead of Fargate, which makes Docker access, VPN support and the full Claude Code sandbox available on AWS; the capacity scales to zero when unused.

**Architecture:** The onboarding module gains an optional per-user compute block: the user's own ECS cluster, an instance role and profile, a launch template on the ECS-optimized AMI, an Auto Scaling group (min 0) and a capacity provider with managed scaling, so instances exist only while a task needs one. An EC2 project registers an EC2-compatible task definition (awsvpc, the host's Docker socket and/or VPN device when enabled) and runs on that cluster through the capacity provider. Everything else (secret, EFS, agent tunnel, stop guard, idle stop, follower, port mappings) is phase 5–6 unchanged.

**Tech Stack:** OpenTofu (user-onboard module, hashicorp/aws 6.73.0 pinned), Rust (aws-sdk-ecs/-ec2 read, pricing), bash entrypoint, React/TS.

**Spec:** `docs/superpowers/specs/2026-11-13-aws-ecs-host-design.md` (Multi-user accounts → strict tenancy "Privileged and Docker allowed only on a per-user capacity provider"; ECS on EC2 vs Fargate; Feature compatibility "EC2 (dedicated)" column; Phase 7). Phase 5 and 6 rulings still bind.

## User decisions (2026-11-16)

- **Idle capacity scales to zero.** The Auto Scaling group has min 0; the capacity provider's managed scaling removes instances when no task needs them. Starts after idle take about 2–3 minutes longer (instance boot + image pull).
- **The instance type is set at onboarding** (default `m7i.large` for x86, `m7g.large` for ARM). Projects only choose Fargate or EC2.
- **No GPU in phase 7.**

## Decisions this plan makes (rulings)

- **E1. A per-user ECS cluster, not a capacity provider on the environment cluster.** `PutClusterCapacityProviders` replaces a cluster's whole list, and the environment module owns the shared cluster's list; two modules writing it would race and undo each other. The user's onboarding module creates `triple-c-<env>-<owner_key>` (the workspace-user policy's `ecs:cluster` condition `cluster/triple-c-*` already matches) with exactly one capacity provider. Strict isolation follows for free: nobody else's task can be placed on the user's instances.
- **E2. Compute is opt-in per onboarding.** New onboarding variables `ec2_instance_type` (empty = no EC2 compute, the default; the module creates nothing for EC2) and `ec2_max_instances` (1–4, default 1). Adding or removing it is an onboarding re-apply. `ONBOARD_MODULE_VERSION` 1 → 2 (re-apply shows "Update available"; existing users keep working on Fargate without it).
- **E3. Instance specifics:** ECS-optimized Amazon Linux 2023 AMI resolved at apply time from the public SSM parameter (`/aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id`, or `…/arm64/…` by the type's architecture); IMDSv2 required, hop limit 2 (tasks can't reach the instance role at hop 1 with awsvpc anyway — awsvpc tasks get no IMDS route; set `ECS_AWSVPC_BLOCK_IMDS=true` in the agent config); root volume gp3 50 GiB encrypted; instances in the environment's two subnets with the environment's tasks security group; `ECS_ENABLE_TASK_ENI` trunking is **not** enabled (one workspace per instance is the expected use; `ec2_max_instances` bounds concurrency).
- **E4. The instance role** `triple-c-<env>-<owner_key>-instance` carries the managed-policy-equivalent inline rights for the ECS agent (register/poll/submit, ECR pull, logs) and SSM core (for ECS Exec on EC2), under the permissions boundary — which therefore grows: the boundary module gains those actions (boundary version bump; an account admin re-applies it once). Instance profile of the same name.
- **E5. Admin tier grows a third file** `aws/policies/environment-admin-compute.json` (the two existing files are at 5,805 and 3,340 of 6,144): `autoscaling:*` on `autoScalingGroup:*:autoScalingGroupName/triple-c-*` with tag conditions, EC2 launch templates tag-scoped (`triple-c:component`), `ecs:CreateCapacityProvider`/`DeleteCapacityProvider`/`UpdateCapacityProvider`/`PutClusterCapacityProviders` on `capacity-provider/triple-c-*` and `cluster/triple-c-*`, `iam:*InstanceProfile*` on `instance-profile/triple-c-*`, `iam:PassRole` to `ec2.amazonaws.com` for `role/triple-c-*`, `ssm:GetParameter` on the public AMI parameters, `ec2:RunInstances` (with launch-template + tag conditions), `iam:CreateServiceLinkedRole` for `autoscaling.amazonaws.com`. Destruction tag-scoped as in phase 3. MODULE_CALLS gains every new provider call (drift test).
- **E6. Docker access on EC2 = the host's socket.** `allow_docker_access` on an EC2 project mounts `/var/run/docker.sock` from the instance (host volume) at the same path, and the entrypoint's existing Docker-socket group step runs in aws mode when the socket exists. That is root on the user's own instance — acceptable only because the instance is theirs alone (E1); the UI says so. **Privileged mode is not offered** separately (nothing in Triple-C needs it beyond Docker/VPN).
- **E7. VPN on EC2 = the same three pieces as local** (`vpn_host_config` parity): `NET_ADMIN`, the `/dev/net/tun` device, and the `net.ipv4.conf.all.src_valid_mark=1` system control (ECS `systemControls`, allowed for awsvpc). The AMI must have the `tun` module (AL2023 does); the live test checks a `wg` interface can be created.
- **E8. The Claude Code sandbox is allowed on EC2** (bubblewrap's user namespaces work on the ECS-optimized AMI; verify live — if not, keep it off like Fargate, P9).
- **E9. EC2 task sizing:** CPU/memory become reservations that must fit the instance type (the app knows the type's vCPU/memory from a small built-in table for the default families, validated at save; unknown types → only a "must fit" warning), no `ephemeralStorage` (instance disk), no Spot (EC2 Spot is a later item).
- **E10. Cost estimate for EC2** = the instance type's on-demand hourly price (Pricing API `AmazonEC2`, Linux, shared tenancy) while running; shown with "instances scale to zero when no workspace is running".

## Global Constraints

- Phase 5/6 constraints hold (sdk_config only; three tag keys on per-user resources; names only in `aws/tofu_modules.rs`; P1; policy + checks + README together, ≤ 6,144 each; three-part command registration; serde defaults + TS mirrors; live AWS only via the scratchpad `awsx`, cleaned up, spend cap $10 overall).
- Module versions and pinning tests move together (HCL `template_version` ↔ Rust consts ↔ default tags).
- Fargate projects behave exactly as before (fingerprints of existing Fargate plans unchanged — pinned tests).
- Every per-user EC2 resource carries `triple-c:component=user-onboarding` via default tags (admin destruction scoping).
